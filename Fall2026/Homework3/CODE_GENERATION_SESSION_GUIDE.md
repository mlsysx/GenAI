# Q6B — Code Generation learning-session guide

This guide supports the **5-point learning session**. It does not add a second programming project, a separate essay, a claim-verification table, or extra mandatory screenshots. Reuse your Q5 agent through the Q6 web/desktop interface.

## Before the session

Record your stated prior knowledge and **two goals**. Possible goals are to (a) turn an underspecified request into a testable function specification and (b) identify what tests do and do not establish about generated code. Use your own goals; do not prefill a claim of mastery.

Use at least **two Code Generation learning sources and one visual**. Retain original citations and section/figure locations. The visual must actually be inspected by the VLM. Add sources using a separate Q6 manifest/configuration snapshot; do not edit frozen Q5 cases/results.

### Optional starting readings

These are verified reading suggestions, not required sources or bundled documents. Retrieve lawful copies, review permissions, and select the relevant sections/figures yourself.

- Chen et al. (2021), *Evaluating Large Language Models Trained on Code*: https://arxiv.org/abs/2107.03374 . Useful for connecting natural-language specifications, generated programs, and functional evaluation. Published results are historical, not current model rankings.
- Liu et al. (2023), *Is Your Code Generated by ChatGPT Really Correct? Rigorous Evaluation of Large Language Models for Code Generation*: https://arxiv.org/abs/2305.01210 . Useful for discussing the limits of a small test suite and code-generation evaluation.
- Python's official `unittest` documentation: https://docs.python.org/3/library/unittest.html . A practical reference for writing assertions and documenting checks. Record the actual version used.

Do not copy this assignment's practice criteria or reference answers into the retrieval index. Your actual source papers/documentation belong in the index; learner attempts, evaluation cases and survey responses do not.

## Suggested progression

1. **Explain:** Ask how a task specification, examples, and constraints guide generated code. Ask a focused follow-up if the explanation is vague.
2. **Inspect a visual:** Select a diagram/chart from a source. Ask what its inputs, outputs, axes or arrows mean and which conclusions it supports. Preserve uncertainty about illegible values.
3. **Specify and generate:** Choose a small pure Python function. State intended behavior and example checks before asking for an implementation. Read the generated code, not only its prose explanation.
4. **Practice:** Have the assistant ask three questions—specification, testing/evaluation, and debugging/limitations. Submit your own attempts before requesting solutions, then examine the feedback. These may use the same function.
5. **Resume:** Save the session, stop/restart the application, restore it, compare the displayed fields with the saved record, and continue. Do not silently reset budgets or reuse old report-write approvals.

The final report may record manual tracing or actual local test runs; **label which occurred**. Generated predictions of test results are not observed execution results. A failing generated function is acceptable when honestly recorded and discussed.

## Optional task card: merge intervals

You may choose another comparably small function. This task card is an authored teaching specification, **not a precomputed model solution**.

**Signature:** `merge_intervals(intervals)`

**Assumptions:** Input is a list of `(start, end)` pairs with finite numeric endpoints and `start <= end`. Invalid inputs are outside this optional specification; define their behavior explicitly if you extend it.

**Expected behavior:** Return a new list sorted by start value. Merge overlapping intervals and intervals that touch at an endpoint. Do not mutate the input. An empty list returns an empty list.

**Candidate checks to design:** unordered intervals; touching intervals; nested intervals; duplicate intervals; empty input; input unchanged after the call. Choose explicit inputs and expected outputs and explain your choice **before** using the generated answer to judge itself. The task card is not a requirement to run all six categories.

**Practice-question types (not supplied answers):**
- Identify a missing constraint in an underspecified interval-merging prompt and improve it.
- Choose an input that distinguishes merging touching intervals from merging only strictly overlapping intervals.
- Explain why passing ordinary examples might miss mutation of the input or a boundary error.

No actual bug must be invented: if you find none, discuss a plausible limitation or additional check and mark it as hypothetical.

## Code-review boundary

The provided agent has no arbitrary Python/shell execution tool. Keep it that way. Display generated code as text. For optional local execution, manually review a short self-contained pure function, use a separate disposable local environment with no credentials or sensitive files, and do not run network/process/file operations. A virtual environment alone is not a security sandbox. Do not report a manual trace as an executed test.

Store the specification, generated snippet and your example-check table under `outputs/q6/` (or another documented Q6 path). These are learning records, not retrieval documents. No prescribed code-accuracy threshold, model benchmark, paid API, or human-participant study is required.
